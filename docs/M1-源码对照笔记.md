## 1. 我的实现 vs 参考项目

| 维度 | 我的 M1 | 参考 MokioAgent |
| --- | --- | --- |
| 架构 | 单 actor 循环（128 行） | 多 agent + LangGraph（code/search agent 专职） |
| 工具 | 5 个（file/grep/bash/registry） | 8 个（+ todo/notepad/web_search） |
| bash_tool | 65 行，简单执行 | 16.9K，超时/截断/背景/shims |
| 规划/记忆载体 | 无 | TodoTool + NotepadTool |
| 错误处理 | 异常捕获返回 {ok:False} | 结构化失败 + 修复循环 |
| 上下文管理 | 消息无限追加 | 压缩/截断设计 |

## 2. 官方比我好的 3 个设计点

1. **bash_tool 的健壮性**（65 行 vs 16.9K）：参考实现有超时上限、长输出截断落盘、fresh shell 隔离、PATH shims（把 python/pip 稳定指向当前环境）——我的一次性执行在大命令/长输出/环境漂移面前都会出问题
2. **规划与记忆工具**：TodoTool（任务拆解持久化）+ NotepadTool（外置大脑）——我的循环"想到哪做到哪"，没有跨轮次的计划载体；这正是 Stage1 里"长任务会迷路"的解药
3. **专职 agent 分离**（code_agent.py）：参考项目把"写代码"职责从通用循环中抽出来，配专属 prompt 和职责边界——我的单 actor 把所有职责压在一起

## 3. 我遗漏的 3 个边界情况

1. **max_loops 耗尽时的交付**：我只 yield error，没有"把已完成的中间结果整理交付"的兜底——用户拿到的是错误而不是部分成果
2. **工具失败后的引导重试**：异常虽然被捕获进 ToolMessage，但"模型是否会从错误中学习并修正"没有机制保障，完全依赖模型自觉——参考项目有明确的修复循环结构
3. **上下文无限增长**：每轮消息持续 append，长任务必然爆上下文——没有任何压缩/截断策略（参考项目有 compaction，是 M5 的内容）

（备选第 4 条：工具参数无 schema 校验，invoke 直接吃 args，非法参数靠工具自己防御）
